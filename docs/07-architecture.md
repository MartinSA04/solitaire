# 07 — Architecture

## The constraint that decides everything

**Static files on GitHub Pages. No server, no build-time secrets, no runtime
network requests.** Everything in [01 — Product brief](01-product-brief.md) that
sounds like a value — no accounts, no tracking, no ads — is also enforced by the
fact that there is nowhere to put them.

Anything that looks like it needs a backend gets solved at build time instead:

| Sounds like a server | Actually |
| -------------------- | -------- |
| Winnable-deal lookup | A 40KB seed list generated by `scripts/` and shipped as a static asset |
| Daily deal | `hash(local date) % pool.length`, computed in the browser |
| Save games, stats | `localStorage` |
| Sharing a deal | A URL query parameter |

## The client framework decision

The scaffolding's README says "no UI framework". That was written before there was a
product to build, and it's the wrong default for this one.

### What the UI actually has to do

Two very different jobs:

1. **The board** — 52 elements whose `transform` is written up to 120 times a
   second by a physics loop, dragged with zero smoothing, and never re-parented.
   See [05](05-interaction-and-motion.md).
2. **The chrome** — a top bar, a bottom bar, a settings sheet with a dozen
   controls, a stats screen, a credits page, a result panel. Ordinary declarative UI
   with ordinary state.

A framework is actively harmful for (1) and clearly helpful for (2).

### Decision: **Svelte 5, one island, with the board held outside reactivity**

`@astrojs/svelte`, a single `client:load` island on the game page.

**Why Svelte over Preact**: it compiles to direct DOM operations with no virtual DOM
diff, so there is no reconciliation pass that might touch a card element between
physics frames. Its runtime is small enough (~4KB for this app's surface) to be
irrelevant on a page whose real payload is a card sprite. And it does not force the
board's imperative code to fight a render model — an effect that writes to a DOM
node it owns is idiomatic Svelte, and a lint-rule violation waiting to happen in
React/Preact.

**Why not vanilla**: the settings sheet, stats screen and result panel are real
stateful UI. Hand-writing them is a few hundred lines of `createElement` and manual
event wiring that will be worse than the equivalent Svelte, and none of it is
performance-sensitive. Purity here buys nothing.

### The rule that makes it safe

> The card layer is **not reactive**. Svelte renders 52 `<div class="card">`
> elements once, after the deal, and never again. A `CardLayer` class holds
> references to them and writes `transform`, `z-index` and `class` directly. Svelte
> state changes may *call into* `CardLayer`; they never re-render it.

Concretely: the 52 cards are inside a `{#key gameId}` block containing a
non-reactive `{#each}` over a frozen array. New deal → new `gameId` → the block is
rebuilt once. Within a game, nothing in the card layer is derived from reactive
state.

Everything else in the island is normal Svelte 5 runes. This is a boring boundary
and it holds as long as it's written down, which is what this paragraph is for.

## Pages and hydration

| Page | Island | Notes |
| ---- | ------ | ----- |
| `/` | `Game.svelte`, `client:load` | The only interactive page |
| `/how-to-play` | none | Static HTML |
| `/credits` | none | Static HTML; licence attributions live here |

Three pages. There is no router, no SPA shell, no view transitions between them.

### First paint

The performance goal from the brief is **under two seconds from cold URL to first
card moved on 4G**. That budget:

- The table, empty slots and chrome are **server-rendered by Astro** and visible
  before any JS runs. The page is never blank.
- The island hydrates and deals. The deal animation (~700ms) covers the card-sprite
  fetch, so the sprite is never a visible delay.
- The card sprite is `<link rel="preload" as="image">` in the head.
- The winnable-seed `.bin` is fetched **in parallel with hydration**, not awaited
  before it — a first deal can come from the URL, a resumed save, or (if the pool
  hasn't landed yet) an unfiltered random seed, with the pool applied from the
  second deal onward. The player never waits on it.
- Fonts are **self-hosted, subset, `font-display: swap`**. No third-party origin,
  per the brief's zero-outbound-requests rule.

Budget: **< 40KB JS gzipped**, **< 15KB CSS**, one ~30KB sprite.

## Persistence

`localStorage`, one key per concern, all namespaced and versioned.

```text
sol:v1:settings     theme, deck, back, drawCount, winnableOnly, sound, timerVisible, reducedMotionOverride
sol:v1:game         the in-progress game (see below)
sol:v1:stats        lifetime counters, per draw mode
sol:v1:records      per-deal bests — a capped LRU map of seed → {time, moves}
sol:v1:daily        last completed daily date, current streak, longest streak
```

### The in-progress game

Resume means restoring an exact position, and the cheapest correct way to do that is
to store **the seed plus the move list**:

```json
{ "seed": 4811209, "draw": 1, "moves": ["d", "t2f", "w t4", "..."], "elapsedMs": 134000 }
```

Replaying moves through `applyMove` on load reconstructs the state exactly, is
impossible to get subtly wrong, and is tiny — a 300-move game is ~1.5KB. It also
means the undo stack survives a refresh for free.

This depends entirely on the frozen shuffle invariant from
[03](03-engine.md): if the seed→deal mapping ever changed, every saved game would
silently become a *different* game. That's the second reason it's frozen.

### Rules

- **Every read is defensive.** `localStorage` throws in Safari private browsing,
  returns `null` when cleared, and may contain anything a user pasted into it. Every
  accessor is wrapped, every parse is validated against a shape, and any failure
  falls back to defaults **silently** — a corrupt save is a new game, not an error
  dialog.
- **The game is fully playable with storage unavailable.** Nothing is awaited on it;
  it is a nicety, not a dependency.
- **Migration**: the `v1` in the key is the schema version. A future `v2` reads `v1`
  if present, writes `v2`, and deletes `v1`. Never a silent in-place reinterpretation.
- **Records are capped** at 500 deals, LRU-evicted. Unbounded growth in
  `localStorage` eventually throws `QuotaExceededError` on a device you don't own.
- **Nothing is ever written that identifies the player.** No IDs, no timestamps
  beyond what the features need, no first-seen date.

## Audio

WebAudio, **synthesised, no sample files**. The entire sound design —
[the pentatonic bounce notes](06-win-sequence.md), card slides, the foundation
chime — is oscillators and filtered noise bursts. Reasons: zero bytes to download,
zero licensing questions, and velocity/pitch mapping is free.

- The `AudioContext` is created lazily **on first user gesture** — browsers block it
  otherwise, and creating one on load is a battery cost for a silent visit.
- Card movement: a short filtered-noise burst, ~25ms, pitch varying slightly per
  move so repeated moves don't machine-gun.
- Foundation drop: a soft sine ping.
- Everything runs through a master gain the mute switch sets to 0 with a 40ms ramp
  (an instant gain change clicks).
- Respects the setting from first load, and the setting defaults to **on** for
  subtle sounds, **which means the first card the player moves makes a small noise**
  — a deliberate choice, since an unexpected sound on a bus is exactly the kind of
  thing that makes someone close a tab. Revisit if it feels wrong in testing; the
  alternative is off-by-default with a one-time hint.

## Build

Unchanged from the scaffolding — `astro build` to `dist/`, deployed by
`.github/workflows/deploy.yml`. Additions:

- `scripts/generate-winnable.ts` is **not** part of `astro build`. It is run
  manually and its output committed, because it takes minutes-to-hours and its
  result must be stable across builds (the daily deal depends on the pool not
  changing). A CI job can verify the committed pool matches what the script produces
  for a sample, but does not regenerate it.
- `scripts/audit-automove.ts` is not part of anything either — not the build,
  not `pnpm test`. It plays a few hundred deals twice over to measure what
  tap-to-auto-move costs, takes a minute or two, and exists to be re-run
  whenever that heuristic is argued about. See the note below.
- No other build step. No image pipeline — the decks are SVG and ship as authored.

## Testing

| Layer | Runner | Covers |
| ----- | ------ | ------ |
| Engine | `node --test` | Everything in [03](03-engine.md) |
| Layout maths | `node --test` | `Layout.ts` is pure: viewport → measurements. Golden values for 360/390/768/1440px, and the "worst-case column fits" assertion. |
| Persistence | `node --test` | Round-trip, corrupt input, missing keys, quota errors, `v1→v2` migration |
| Interaction | Playwright | Deal, drag, tap-to-auto-move, undo, hint, stock recycle, resume-after-reload, deal-from-URL |
| Visual | Playwright | Screenshot per theme × deck at three viewports. Catches theme-token regressions, which no unit test can. |
| Performance | Playwright traces | Frame times for deal, drag and the full win sequence on a throttled profile |
| Site invariants | `node --test` | The existing three-file canonical-host check |

The **win sequence needs a deterministic mode for testing**: `?winseed=N` seeds
the physics PRNG and fixes the timestep, so the visual and performance tests
compare like with like, and `?win` runs the whole thing without a game having
been won. Without them, nothing about Stage 2 is testable. Both are documented
in [06](06-win-sequence.md); neither touches the deal.

## What isn't decided yet

Flagged rather than hidden:

- **Whether the auto-move heuristic in [05](05-interaction-and-motion.md) is
  right.** Half of this is now measured rather than argued.
  `scripts/audit-automove.ts` plays a greedy player's games twice over the same
  deals — once playing its moves, once tapping the cards those moves name and
  letting the heuristic choose — and the tapped run *wins more*: 53.5% against
  51.0% at draw-1 over 400 deals, 17.5% against 16.5% at draw-3. It sends a
  card somewhere unasked on 2.2% of taps, and almost every one of those is rule
  1 declining to send a card home while the tableau could still want it, which
  is the rule doing exactly what it was written to do. The arbitrary tie-break
  between equal columns turns out to fire on under 1% of taps and to be worth
  nothing either way. So the heuristic does not lose games. Whether it picks
  the move you *wanted* is the other half, it is the half the bar in
  [09](09-roadmap.md) actually asks about, and it can only be judged by
  playing.
- **Sound on by default** (above). Genuinely uncertain.
- **Pool size and daily-pool freezing** — 4,096 frozen daily seeds is ~11 years,
  which is probably fine and is trivially extensible by appending, but the
  append-only discipline needs to survive contact with a future regeneration.
- **Whether the Minimal deck can carry the default experience at 46px** or whether a
  sourced deck reads better. A legibility test at phone size decides it, not taste.
